## 目的

このレポートは、PDF2Excel のような中規模機能を Microsoft Copilot に実装させるときに、最短で破綻しにくい進め方を整理したものです。  
特に、次のような問題を避けることを目的にしています。

- 1回のプロンプトで範囲を広げすぎて、実装が崩れる
- コンテクスト不足で既存仕様を壊す
- テスト、ドキュメント、周辺修正が抜ける
- 途中で Copilot が前提を見失い、別物を作り始める

## 前提

このレポートでは、コード実装を行う Copilot を前提にしています。  
具体的には、VS Code 上の GitHub Copilot Chat / Copilot Edits 系の使い方を想定しています。  
単なる文章生成系 Copilot ではなく、「ファイルを読んで、差分を作る」タイプの Copilot に対する運用方法です。

## 結論

最短で実現する方法は、最初から大きな要求を丸投げしないことです。  
正攻法は、次の 3 原則で進めることです。

1. 最初に人間側で「正解の土台」を 1 枚に圧縮する
2. 実装は 1 機能 1 目的の小さな単位に切る
3. 各ターンの終わりに、差分確認とテスト結果を必ず固定フォーマットで返させる

つまり、Copilot を「全部わかっている開発者」として扱うのではなく、「いま渡した範囲だけを高速にこなす実装担当」として使うのが最短です。

## なぜ 1 回で実装させると失敗しやすいのか

Copilot に 1 回で大きな改修をさせると、次の失敗が起きやすくなります。

- 既存仕様の把握が浅くなる
- 変更範囲が広がり、影響範囲の見積もりが甘くなる
- 一部の要求だけ満たして、テストやドキュメント更新が漏れる
- 途中で「それっぽい実装」を優先し、既存設計との整合が崩れる
- 長い会話の途中で、前半の制約を忘れる

これを防ぐには、Copilot に「全体を考えさせる」のではなく、「いまやる作業を限定して、その代わり確認責任も持たせる」設計にする必要があります。

## 最短ルートの全体像

おすすめの流れは次の通りです。

1. 人間側で実装対象を 4〜6 個の作業単位へ分割する
2. 最初に Copilot へ「全体方針」と「今回の担当範囲」だけ渡す
3. 1 単位ごとに、対象ファイル、禁止事項、受け入れ条件、確認コマンドを明示する
4. Copilot の変更後は、必ず差分とテスト結果を短く要約させる
5. 次のターンでは、前ターンの結果要約だけを持ち越し、全文脈を再送しない

この方法の良い点は、毎回の文脈が小さく、判断もぶれにくいことです。

## 役割分担

### 人間側がやること

- 実装範囲の分割
- 正式な仕様の固定
- どのファイルを触らせるかの指定
- 受け入れ条件の決定
- テスト結果の最終確認

### Copilot 側にやらせること

- 対象ファイルの読解
- 限定範囲の実装
- 差分の整合確認
- 指定されたテストの実行
- 変更点の要約

## Copilot に渡すべき最小コンテクスト

毎回のプロンプトには、最低でも次の 6 点だけを入れます。

1. 今回の目的
2. 触ってよいファイル
3. 触ってはいけない範囲
4. 守るべき仕様
5. 受け入れ条件
6. 実行してほしい確認コマンド

逆に、不要な背景説明や過去議論を入れすぎると、Copilot の判断がぼやけます。

## 1 回ごとの理想的な粒度

1 ターンでやらせる作業は、次のどちらかに収まる範囲が適切です。

- 1 つのユーザー価値
- 1 つの技術責務

よくない分け方:

- UI 変更、設定追加、テスト追加、ドキュメント更新を全部 1 回で要求する
- 仕様検討と実装を同時にやらせる
- 例外処理、正常系、運用文書を全部まとめて投げる

よい分け方:

- 実行前チェックだけ
- プロファイル読込だけ
- Summary シートだけ
- Errors の分類だけ
- 最後にテストと文書だけ

## この機能に対する最適な分割案

今回の 4 機能を Copilot に実装させるなら、次の 5 分割が最も速いです。

### Step 0. 読解と変更計画

目的:

- 既存構成を理解させる
- 変更対象ファイルを絞る

対象:

- `scripts/run_pdf2excel.ps1`
- `scripts/build_excel_template.ps1`
- `template/vba/PDF2ExcelMacros.bas`
- `tests/run_integration_tests.ps1`
- `README.md`
- `docs/01-current/01-user-manual.md`

期待成果:

- 変更方針の要約
- どの機能をどのファイルで実装するかの整理

### Step 1. 実行前チェック画面

目的:

- 変換前に対象件数、保存先、プロファイル、代表ファイルを表示する

対象:

- `scripts/run_pdf2excel.ps1`
- 必要なら `run_pdf2excel.bat`

受け入れ条件:

- 実行前に確認表示が出る
- `Y/N` で続行可否を選べる
- 自動実行用に確認スキップ手段がある

### Step 2. 帳票プロファイル機能

目的:

- JSON ベースで帳票設定を切り替えられるようにする

対象:

- `config/profiles/default.json`
- `scripts/run_pdf2excel.ps1`

受け入れ条件:

- 既定プロファイルで従来動作する
- `-ProfileName` または `-ProfilePath` で切り替えられる
- 想定列数とヘッダー除外行数をプロファイルから読める

### Step 3. 実行結果サマリー強化

目的:

- `Summary` シートと `Control` シートを拡張する

対象:

- `scripts/run_pdf2excel.ps1`
- `scripts/build_excel_template.ps1`
- `template/vba/PDF2ExcelMacros.bas`

受け入れ条件:

- `Summary` シートが出る
- 成功 PDF 数、失敗 PDF 数、取込行数、処理時間が見える
- PDF 別の取込件数が見える

### Step 4. エラー分類の明確化

目的:

- `Errors` シートにエラーコードと分類を持たせる

対象:

- `scripts/run_pdf2excel.ps1`
- `docs/01-current/02-troubleshooting.md`

受け入れ条件:

- `ErrorCode`
- `ErrorCategory`
- `UserMessage`
- `TechnicalDetail`

が出ること

### Step 5. テストと文書更新

目的:

- ここまでの差分を壊さず確定する

対象:

- `tests/run_integration_tests.ps1`
- `README.md`
- `docs/01-current/01-user-manual.md`
- `docs/01-current/03-project-layout.md`
- `docs/01-current/02-troubleshooting.md`

受け入れ条件:

- 新機能に対応したテストが追加される
- ドキュメントに新しい操作手順が追記される

## もっとも効くコンテクスト管理方法

最短で安定するのは、「毎ターンごとに全文脈を再送しない」方法です。  
代わりに、各ターンの冒頭で次の 3 つだけを持たせます。

1. 現在の目的
2. 前ターンの結果要約
3. 今回の受け入れ条件

### 推奨する持ち回りフォーマット

```text
前回までの確定事項:
- 実行前チェックは実装済み
- NoConfirm は追加済み
- 既存テストは壊れていない

今回やること:
- 帳票プロファイル機能だけを実装する

今回触ってよいファイル:
- scripts/run_pdf2excel.ps1
- config/profiles/default.json

触ってはいけないこと:
- Summary シート追加はまだやらない
- Errors の列追加はまだやらない

受け入れ条件:
- default プロファイルで従来動作
- ProfileName/ProfilePath で切り替え可能
```

この形式にすると、Copilot が「何を覚えていればよいか」を見失いにくくなります。

## 最初に渡すべき基礎プロンプト

最初のターンでは、いきなり実装ではなく、読解と実装計画だけさせるのが最も効率的です。

```text
このリポジトリで、PDF2Excel の機能改善を段階実装したいです。
まずは実装せず、次だけ行ってください。

1. 既存の実装構成を把握する
2. 次の4機能をどのファイルで実装すべきか整理する
3. 実装順を 4〜6 ステップに分割する
4. 各ステップの受け入れ条件を簡潔に書く

対象機能:
- 実行前チェック画面
- 帳票プロファイル機能
- 実行結果サマリー強化
- エラー分類の明確化

読む対象:
- scripts/run_pdf2excel.ps1
- scripts/build_excel_template.ps1
- template/vba/PDF2ExcelMacros.bas
- tests/run_integration_tests.ps1
- README.md
- docs/01-current/01-user-manual.md

出力形式:
- 変更対象ファイル一覧
- ステップ分割
- 各ステップの受け入れ条件
- リスク

この段階ではコード変更しないでください。
```

## 実装ターンで使う標準プロンプト

以下の形に固定すると、Copilot のぶれが減ります。

```text
前回までの確定事項:
- {前回までの要約}

今回やること:
- {今回の作業だけを書く}

今回触ってよいファイル:
- {ファイル1}
- {ファイル2}

触ってはいけないこと:
- {今回やらないこと}

守るべき仕様:
- {仕様1}
- {仕様2}

受け入れ条件:
- {条件1}
- {条件2}

作業内容:
1. 対象ファイルを読んで必要最小限の変更を行う
2. 変更後に関連テストを実行する
3. 最後に次を報告する
   - 変更ファイル
   - 変更内容の要約
   - 実行したテスト
   - 残課題

必要なら実装前に、変更方針を3〜6行で先に出してください。
```

## 不具合修正ターン用プロンプト

Copilot は「新規実装」より「失敗した差分のピンポイント修正」のほうが得意です。  
そのため、失敗時は再度大きな依頼をせず、不具合だけを切り出して渡すべきです。

```text
前回の実装で次の不具合が出ました。

症状:
- {症状}

再現方法:
- {再現手順}

エラー:
- {ログや例外}

今回の目的:
- 原因を特定し、最小変更で修正する

触ってよいファイル:
- {対象ファイル}

触ってはいけないこと:
- 新機能追加
- 別機能のリファクタリング

受け入れ条件:
- {不具合が再現しなくなる条件}
- 既存テストが通ること

最後に、原因、修正内容、テスト結果を簡潔に報告してください。
```

## Copilot に必ず守らせるべきルール

次のルールを毎回プロンプトに明示すると、事故が減ります。

- 今回の範囲外のリファクタリングをしない
- 関連しないファイルは触らない
- 既存仕様を変える場合は明示する
- テストを実行してから報告する
- 失敗した場合は推定原因を書く
- 不明点がある場合は実装前に仮定を宣言する

## 一番やってはいけない依頼の仕方

次のような依頼は、速そうに見えて実際は遅くなります。

### 悪い例

```text
この機能を全部まとめていい感じに実装して。
必要ならテストやドキュメントも直して。
```

問題点:

- 範囲が広すぎる
- 何をもって完了か不明
- 失敗時にどこが壊れたか切り分けにくい
- Copilot が勝手に設計変更しやすい

## 最短で進めるための実運用テンプレート

おすすめは、次の 1 セットを毎ステップで回すことです。

1. 読ませるファイルを限定する
2. 1 つの目的だけ実装させる
3. テストコマンドを指定する
4. 差分要約を返させる
5. 次のステップ用に「前回までの確定事項」を人間が 5 行以内で再要約する

## この案件での最短実行シナリオ

今回の 4 機能に限れば、Copilot への最短ルートは次です。

1. Step 0 で実装計画だけ作らせる
2. Step 1 で実行前チェックだけ実装
3. Step 2 でプロファイルだけ実装
4. Step 3 で Summary / Control の拡張だけ実装
5. Step 4 で Errors 分類だけ実装
6. Step 5 でテストとドキュメントだけ実装

この順番が良い理由は、依存関係が素直だからです。

- 実行前チェックは独立している
- プロファイルは後続 2 機能の前提になる
- Summary はプロファイルが先にあると作りやすい
- Errors 分類は Summary と文書へ横展開しやすい
- テストと文書は最後にまとめたほうが整合しやすい

## さらに速くする補助策

もし人間側で少し準備できるなら、次を先に作っておくと Copilot の成功率がかなり上がります。

- `変更対象ファイル一覧`
- `既存仕様メモ`
- `今回やらないこと`
- `受け入れ条件一覧`
- `確認コマンド一覧`

つまり、Copilot に設計判断まで丸投げしないことが重要です。

## おすすめの最終出力形式

Copilot の各ターンの最後に、次の形式で必ず返させると管理が楽になります。

```text
変更ファイル:
- ...

実装内容:
- ...

実行したテスト:
- ...

結果:
- PASS / FAIL

残課題:
- ...

次にやるべきこと:
- ...
```

この形式だと、そのまま次ターンの「前回までの確定事項」に使えます。

## 結論

Microsoft Copilot にこの種の機能を最短で実装させる方法は、長い 1 回の依頼ではなく、短い実装ターンを連結することです。  
その際の本質は、「Copilot の文脈量を増やすこと」ではなく、「毎回必要な文脈だけを固定フォーマットで渡すこと」です。

したがって、最良の進め方は次の通りです。

1. 最初に読解専用ターンを置く
2. 実装は 1 機能 1 ターンに切る
3. 毎ターンで対象ファイル、禁止事項、受け入れ条件を固定する
4. 各ターン後にテスト結果と差分要約を回収する
5. 次ターンへは要約だけを持ち越す

この方法が、最も速く、最も壊れにくく、途中で立て直しやすい方法です。
