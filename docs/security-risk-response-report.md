# PDF2Excel セキュリティリスク対応レポート

- 作成日: 2026-03-16 01:02 JST
- 作成者: Codex (GPT-5)
- 更新日: 2026-03-16

## 1. 目的

本レポートは、[system-risk-evaluation.md](system-risk-evaluation.md) で指摘されているセキュリティリスクについて、現状の問題、対応案、各案のメリット・デメリットを整理するものです。  
対象は主に次の論点です。

- 一時作業領域 `staging` / `runtime` への機密データ残留
- 共有環境での閲覧リスク
- `ExecutionPolicy Bypass` 常用による監査・統制上のリスク
- ログや運用情報からの副次的な情報露出

## 2. 結論

現時点で最も費用対効果が高いのは、次の4点です。

1. runtime / staging を共有領域ではなくローカル領域へ移す
2. 失敗時だけ一時ファイルを即時削除し、成功時は現状維持とする
3. `Secure` モードでは `input` 同期を止める
4. 本番導線から `ExecutionPolicy Bypass` を段階的に外し、配布用 ZIP では `Bypass` を禁止する

一方で、これらはすべてトレードオフを伴います。  
特に、障害調査のしやすさ、導入の容易さ、サポート負荷は悪化します。

なお、初期実装の適用先は `VER2` の本番導線に限定するのが妥当です。  
`VER1` と開発・テスト導線は現状維持とし、配布用 `V2` ZIP の起動導線から順に反映するのが安全です。

## 3. 問題・対応案・メリット・デメリット

### 3-1. 問題1: `staging` / `runtime` に機密PDFや一時xlsmが残る

**問題**  
処理途中や異常終了時に、`output/runtime/runs/.../staging` や `runtime` に機密データを含む PDF / xlsm が残る可能性があります。  
現在の「次回起動時の cleanup」は可用性対策としては有効ですが、機密保護としては弱いです。

**対応案A: 正常終了・異常終了の両方で即時削除する**  
メリット:
- 機密残置時間を最小化できる
- 共有環境や端末紛失時の露出時間を短縮できる
- セキュリティ説明が明快になる

デメリット:
- 障害調査がかなり難しくなる
- 再現に必要な現物が残らない
- Excel や COM がまだ掴んでいると cleanup 自体が新たな失敗要因になる

**対応案B: 失敗時だけ即時削除し、成功時は現状維持**  
メリット:
- 最も危ない「異常終了時残置」を先に潰せる
- 正常系の運用や調査性は比較的維持できる

デメリット:
- 成功時にも一時データは短時間存在する
- 実装条件分岐が増える
- 「何を失敗とみなすか」の整理が必要

**対応案C: 既定は即時削除、管理者だけ残置オプションを使えるようにする**  
メリット:
- 既定の安全性と調査性の両立がしやすい
- デバッグ用途を明示運用へ隔離できる
- 実務上の落としどころとして現実的

デメリット:
- オプション管理が必要
- 誰が残置を許可できるかの運用ルールが要る
- 結局「残置モード」が常態化する危険がある

**推奨**  
案B。

### 3-2. 問題2: 共有フォルダ上の runtime が他ユーザーに見える

**問題**  
共有フォルダや共通作業ディレクトリ上で runtime/staging を作ると、異常終了時や cleanup 前に別ユーザーが参照できるリスクがあります。

**対応案A: runtime を `%LOCALAPPDATA%\\PDF2Excel\\runtime` に移す**  
メリット:
- ユーザー単位で隔離しやすい
- 共有フォルダ露出を大幅に減らせる
- Windows 権限モデルと相性が良い

デメリット:
- サポート時に現物の場所が分かりにくくなる
- 端末ごとに場所が変わる
- ローカル端末側の保護責任が増える

**対応案B: runtime を `%TEMP%\\PDF2Excel\\runtime` に移す**  
メリット:
- 浅いパスになりやすく、cleanup しやすい
- 一時領域として意味が明確
- 共有領域から切り離しやすい

デメリット:
- TEMP の掃除方針は端末依存
- 一時フォルダ監視製品や OS 挙動の影響を受けやすい
- 保持性が低く、調査証跡が消えやすい

**対応案C: `Secure` モードでは共有パス実行自体を拒否する**  
メリット:
- ルールが明快
- 共有環境起因の漏えいを構造的に避けられる

デメリット:
- 共有フォルダ前提の現場運用と衝突する
- UX 上は「急に使えなくなった」と見えやすい
- 例外運用の要求が出やすい

**推奨**  
案A を基本にし、`Secure` モードで案Cを併用する。

### 3-3. 問題3: `input` フォルダにもPDFを同期して保持する

**問題**  
`input` は保管用途であり、`staging` より滞留期間が長くなりやすいです。  
特に機密 PDF を毎回同期する設計は、不要な複製を増やします。

**対応案A: `Secure` モードでは `input` 同期を無効化する**  
メリット:
- 機密コピーを減らせる
- データ滞留期間を短くできる
- セキュリティ方針が分かりやすい

デメリット:
- 再実行性が落ちる
- サポート時に「前回処理した PDF」が残らない
- 利用者には少し不便

**対応案B: `input` は残すが、自動削除期間を短くする**  
メリット:
- 運用利便性を保ちやすい
- いきなり UX を壊さない

デメリット:
- 機密残置自体は続く
- 削除タイミング管理が必要
- 共有環境ではまだ不十分

**対応案C: `KeepInput` 使用時のみ強い警告を出す**  
メリット:
- 既存運用を壊さず注意喚起できる
- 実装影響が小さい

デメリット:
- リスクは本質的に減らない
- 注意喚起だけで終わる

**推奨**  
案A。

### 3-4. 問題4: `ExecutionPolicy Bypass` を本番導線で常用している

**問題**  
BAT、メニュースクリプト、本体スクリプトの起動例で `Bypass` を広く使っています。  
これは監査やセキュリティレビューで問題視されやすいです。

**対応案A: 本番導線から `Bypass` を外し、`RemoteSigned` 前提へ移行する**  
メリット:
- 監査上の説明がしやすい
- 本番利用の統制レベルを上げられる
- 「例外実行」が常態化しない

デメリット:
- 初回導入が面倒になる
- 配布方法によっては実行ブロックが増える
- 利用者サポート負荷が上がる

**対応案B: コード署名を導入する**  
メリット:
- エンタープライズ監査で最も筋が良い
- 配布物の正当性を示せる
- `RemoteSigned` やより厳格な運用へ進みやすい

デメリット:
- 証明書調達・更新・失効管理が必要
- 配布工程が重くなる
- 証明書トラブル自体が新たな障害原因になる

**対応案C: 本番用と開発用を分離し、`Bypass` は開発/テストだけに残す**  
メリット:
- 現実的な移行ステップを作れる
- 開発速度を大きく落とさずに済む
- 本番導線だけ先に監査対応できる

デメリット:
- 起動導線が複数になる
- 手順書や資料の整備が必要
- 混在運用になると混乱しやすい

**推奨**  
案A + 案C。配布用 ZIP に含める本番導線では `Bypass` を禁止し、開発/テスト導線だけを暫定的な例外扱いとする。将来的には案Bへ進む。

### 3-5. 問題5: ログにフルパスや運用情報が出すぎる

**問題**  
ログや Control 情報に、入力フォルダ、staging パス、出力先などが残ると、運用情報の露出につながります。

**対応案A: 既定ログからフルパス出力を減らす**  
メリット:
- 情報露出を抑えられる
- 利用者向け既定動作として分かりやすい

デメリット:
- 障害調査が遅くなる
- ログだけでは状況再現が難しくなる

**対応案B: `Debug` モードだけ詳細ログにする**  
メリット:
- 通常運用と調査時を分けられる
- 実務上のバランスが良い

デメリット:
- モード切り替えの理解が必要
- Debug ログの保護ルールが別途必要

**対応案C: `Secure` モードではファイル名も最小化する**  
メリット:
- 最も安全寄り
- 利用実態の露出を減らせる

デメリット:
- 運用性が大きく落ちる
- ユーザーやサポート担当が見ても分かりにくい

**推奨**  
案A + 案B。

### 3-6. 問題6: `run.lock` や実行中情報から利用状況が読める

**問題**  
`run.lock` に実行者情報や状態を書きすぎると、副次的な情報露出になります。

**対応案A: `run.lock` の記録内容を最小化する**  
メリット:
- 露出を減らせる
- 実装変更が比較的小さい

デメリット:
- 誰がロックしているか追いにくくなる
- サポート性が下がる

**対応案B: 実行者情報はローカルだけに残し、共有場所へは出さない**  
メリット:
- 情報露出と調査性のバランスが良い
- 運用面でも使いやすい

デメリット:
- 保存先を分ける設計が必要
- 実装が少し複雑になる

**対応案C: `run.lock` 自体をローカル runtime 側へ寄せる**  
メリット:
- 共有環境への情報露出を減らせる
- runtime ローカル化と整合が取れる

デメリット:
- 多重実行制御の見直しが必要
- 既存の監視・サポート前提が変わる

**推奨**  
案B + 案C。

### 3-7. 問題7: 「デバッグのために残す」が常態化する

**問題**  
セキュリティ強化を入れても、現場で常時 `KeepRuntimeOnError` のような運用になると意味が薄れます。

**対応案A: 既定は削除、例外時だけ明示オプションで残す**  
メリット:
- 既定値を安全側に寄せられる
- 方針が明確

デメリット:
- 調査時の手順が増える
- 例外運用の管理が必要

**対応案B: 管理者または保守担当だけが残置を使えるようにする**  
メリット:
- 濫用を防ぎやすい
- ガバナンスを持たせやすい

デメリット:
- 権限管理が必要
- 現場では使いにくくなる

**対応案C: 残置する場合も専用保護領域に限定する**  
メリット:
- 露出リスクを下げつつ調査性を確保できる
- 運用ルールにしやすい

デメリット:
- 保存先設計が必要
- 保護領域のアクセス制御が別途必要

**推奨**  
案A。必要に応じて案C。

### 3-8. 問題8: 文書の「完備」「完全セルフクリーン」表現が過大

**問題**  
現在の文書表現は、可用性・運用性の評価としては理解できても、セキュリティ評価としては強すぎます。

**対応案A: 「通常運用では十分」に表現を弱める**  
メリット:
- 誤解を減らせる
- 実態に近い説明になる

デメリット:
- 見た目の評価は少し下がる

**対応案B: 可用性評価とセキュリティ評価を分離する**  
メリット:
- 説明が整理される
- 監査で使いやすい

デメリット:
- 文書が長くなる
- 更新コストが少し増える

**対応案C: 高機密運用は追加対策必須と明記する**  
メリット:
- スコープ誤認を防げる
- 導入判断がしやすい

デメリット:
- 「すぐ導入可能」という印象は弱まる

**推奨**  
案A + 案B + 案C。

## 4. 推奨対応セット

### 推奨セット1: 現実的な標準対応

- runtime/staging をローカル領域へ移す
- 失敗時だけ即時削除し、成功時は現状維持
- `Secure` モードでは `input` 同期を無効化
- 既定ログは最小化し、Debug のみ詳細化
- 本番導線から `Bypass` を段階的に外し、配布用 ZIP では `Bypass` を禁止する

**メリット**
- セキュリティ効果と運用現実性のバランスが良い
- 一気に壊しにくい
- 監査説明もしやすくなる

**デメリット**
- 利用者説明が増える
- サポート負荷は上がる
- 障害調査のやり方を見直す必要がある

### 推奨セット2: 監査重視の強化対応

- 推奨セット1に加え、コード署名導入
- 共有パス実行拒否
- 残置ファイルは管理者限定オプションへ
- セキュリティ診断機能を追加

**メリット**
- 監査・統制には最も強い
- 企業導入時の説明力が高い

**デメリット**
- 導入コストが高い
- 配布・更新・保守が重くなる
- 現場 UX はかなり落ちる

## 5. 優先順位

1. runtime/staging のローカル化
2. 失敗時の即時削除
3. `Secure` モードでの `input` 同期停止
4. ログ最小化
5. 本番導線からの `Bypass` 除去
6. コード署名
7. 共有パス拒否
8. セキュリティ診断機能

## 6. 総評

最大の問題は、`Bypass` そのものよりも、**機密データを含む一時ファイルが共有・残置され得ること**です。  
したがって、最優先は runtime/staging の扱いの見直しです。

一方で、セキュリティ強化は必ず UX と調査性を削ります。  
そのため、「既定は安全側」「調査時だけ明示オプションで緩める」という運用設計が最も現実的です。

推奨としては、まずは次の組み合わせが妥当です。

- runtime をローカル化する
- 失敗時だけ即時削除し、成功時は現状維持とする
- `Secure` モードでは `input` を残さない
- 本番導線から `Bypass` を外し、配布用 ZIP では `Bypass` を使わない

これが、現状の PDF2Excel のアーキテクチャを大きく壊さずに、セキュリティリスクを実際に下げる最小有効セットです。
