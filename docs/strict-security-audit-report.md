# PDF2Excel セキュリティ評価レポート (辛口監査版)

- 作成日: 2026-03-16 00:00 JST
- 評価対象: PDF2Excel プロジェクト全体 (V1/V2 含む)
- 評価者: Codex (GPT-5)
- 更新日: 2026-03-20

注記:

- 正式運用導線は現在 `run_pdf2excel.bat` = `VER2 Secure` + `RemoteSigned` です。
- 本文中の `ExecutionPolicy Bypass` 指摘は、旧導線、保守用スクリプト、テスト・個別コマンドを含む厳しめ評価として読んでください。

## 1. エグゼクティブ・サマリ (総評)

**【評価結果】 落第点（エンタープライズ本番環境への投入は極めて危険）**

現在の PDF2Excel システムは、「動くこと」や「エラーからの自動復旧（可用性）」に極端にパラメータが振られており、セキュリティ設計の観点からは**PoC（概念実証）レベルを脱していません**。特に機密情報を含む帳票（人事給与、顧客情報、建設業の単価情報など）を扱う領域において、現状のアーキテクチャのまま共有サーバーや共用端末で無自覚に稼働させることは、重大な情報漏洩インシデントの直接的な引き金となります。

「自動エラー回復」や「次回起動時のクリーンアップ」といった可用性重視の仕組みが、皮肉にも**「異常終了・クラッシュした機密データ（PDFや中間生成のxlsm）をシステム上に長時間平文で放置・陳列する」**という最大の脆弱性を生み出しています。

早急にアーキテクチャの根本的な見直し（Secure by Defaultへの転換）が極めて強く推奨されます。

---

## 2. 致命的な脆弱性とセキュリティリスク

### 💥 V-1: 機密データの平文長期残置と「ゴミ屋敷」アーキテクチャ
**【深刻度: Critical (緊急)】**
- **事象**: 処理対象の機密PDFを、処理のために `staging` や `runtime` フォルダへ物理的にコピーする設計となっています。処理が例外でクラッシュ（Excelのハングアップ等）すると、**コンテキストがそのまま放棄され、次回システムが起動されて `Compact-RuntimeArtifacts` が走るまで、機密PDFと中間データが平文のまま無防備に残置**されます。
- **攻撃シナリオ**: 共有フォルダで運用されている場合、処理が異常終了した直後から、権限のない別ユーザーが `runtime/runs/...` ディレクトリを覗き見ることで、他部門の機密帳票を容易に閲覧・持ち出し可能です。
- **評価**: いわゆる「ゴミ掃除は次回起動時にやればいい」という設計思想であり、セキュリティ上は最悪のアンチパターンです。機密データのライフサイクル管理が完全に崩壊しています。

### 💥 V-2: `ExecutionPolicy Bypass` の無自覚な濫用とバックドア・リスク
**【深刻度: High (高)】**
- **事象**: V2のBATファイル等で `RemoteSigned` へ移行しようとした痕跡は認められますが、システムの仕様の奥深く（`build_excel_template.ps1` 呼び出し箇所等）やテストスクリプト群において、依然として **`ExecutionPolicy Bypass` がハードコードされてベタ書き** されています。
- **攻撃シナリオ**: 攻撃者（またはランサムウェア）がシステムのフォルダ内に悪意のある PowerShell スクリプトを紛れ込ませた（あるいは既存のスクリプトを改ざんした）場合、このシステムを利用するユーザー（またはタスクスケジューラの特権）のコンテキストで、何の警告・ブロックもなく `Bypass` で悪意あるコードが即座に実行されます。
- **評価**: 監査が入れば一発で「重大な不適合（レッドカード）」となる実装です。`Bypass` は開発者のデバッグ用オプションであり、常設業務システムに組み込んで稼働させるものではありません。

### 💥 V-3: コントロール不能なCOMオブジェクトとサニタイズ（完全消去）の阻害
**【深刻度: High (高)】**
- **事象**: 外部プロセスである `Excel.exe` のCOMを操作してデータを流し込んでいますが、Excelプロセスがフリーズ・クラッシュしてファイルをロック（掴んだまま）状態になった場合、現在の PowerShell 側のエラーハンドリングではファイルの削除（サニタイズ）がOSの排他制御によって拒否されます。
- **攻撃シナリオ**: 機密データを含んだ一時ファイルが「消したくても消せない」状態に陥り、サーバーや利用端末が手動再起動されるまで長期間ディスク上に晒され続けます。
- **評価**: PowerShell側とCOM側の非同期的なライフサイクルのズレを考慮しておらず、「異常時であっても確実に物理消去（Secure Erase）できる」という保証がシステムアーキテクチャ上担保されていません。

### 💥 V-4: ログやロックファイルを通じたインフォメーション・ディスクロージャー
**【深刻度: Medium (中)】**
- **事象**: ログファイル (`logs/run_*.log`) に対し、システム内の完全なファイルパス等の運用状況が平文で出力されます。また、多重起動防止用の `run.lock` には `$env:USERNAME` や `$env:COMPUTERNAME` が平文で記録され、共有フォルダに露出しています。
- **攻撃シナリオ**: パス名そのものに顧客名やプロジェクト名が含まれていた場合、ログファイルへのアクセス権限さえあれば、実際のPDFが見えなくても「誰が・いつ・どの企業と取引しているか」といった機密情報を推測・取得可能です。
- **評価**: ログとロックファイルのマスキング（匿名化）設計が欠落しており、サポート担当者や運用者の利便性がセキュリティ実装を露骨に凌駕してしまっています。

## 3. 実行すべき是正措置 (Immediate Actions Required)

本システムを、名実ともに本番投入可能なエンタープライズ品質に引き上げるためには、以下の根本的改修（リアーキテクチャ）が必須です。

### 🔪 Action 1: 「残置させない」完全同期型セキュアワイプの実装
- `try...catch...finally` の **`finally` ブロック** において、例外の有無に関わらず、同コンテキスト内で生成された **`staging` および `runtime` 下の対象プロセスの一時ファイルを即時かつ物理的に完全削除** する強制ワイプ処理を絶対に実装してください。
- Excelプロセスがファイルをロックして削除に抵抗している場合は、当該のプロセスID (PID) を特定して `Stop-Process -Force` で殺してでもファイルを消破する、非情かつ確実なエラーリカバリが不可欠です。

### 🔪 Action 2: 共有環境（ネットワークドライブ）での作業領域の完全禁止
- 一時的な作業ディレクトリ (`$runtimeRootDir` 等) は、いかなる場合も共有フォルダ上での作成を許さず、実行ユーザーの強力な権限管理下にあるローカルセキュア領域（例: `%LOCALAPPDATA%\PDF2Excel\runtime` 等）に強制的に固定してください。
- 共有フォルダ上の `$inputDir` に PDFファイルをコピー・保持する既存の「緩い」運用オプション(`KeepInput`) は、セキュリティの観点から即時廃止（非アクティブ化）すべきです。

### 🔪 Action 3: `Bypass` の徹底パージとコード署名 (Code Signing) の導入
- システム全体（すべてのテストスクリプトを含む）から `-ExecutionPolicy Bypass` の文字列を1行残らずパージしてください。
- 全 `.ps1` ファイルに対して社内の信頼された認証局（CA）から発行されたコード署名証明書で電子署名を行い、`AllSigned` もしくは `RemoteSigned` 環境下でのみ稼働するよう厳格に統制してください。

### 🔪 Action 4: メモリドリブン（ストリーム処理）アーキテクチャへの転換 (中長期)
- 物理ファイル（PDFやxlsm）をいちいちディスクに書き出し・コピーして処理する現在の「物理ファイル依存アーキテクチャ」は時代遅れです。極力メモリ上のストリーム操作でデータをリレーし、ディスク上に痕跡を残さない方式へ転換することを将来のロードマップロードマップに組み込んでください。

---

**【総括】**
現在のシステムは**「性善説」**と**「いずれ正常に片付くこと」**を前提としすぎています。攻撃者や社内の内部不正者の視点に立ち、**「システムが崩壊・クラッシュした直後の最も無防備な瞬間に、データがどう保護されるか」**をゼロベースで再設計しない限り、真のエンタープライズ・セキュリティには到達できません。
