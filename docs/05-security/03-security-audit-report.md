## 1. 識別された主要なセキュリティリスク

### 🚨 リスク1: `ExecutionPolicy Bypass` の常態化 (高リスク)
**箇所**: `run_pdf2excel_v1.bat`, `run_pdf2excel_v2.bat`, およびすべての `_menu.ps1` ファイル等
**内容**: 
PowerShellスクリプトの呼び出しコマンドライン引数において、一律で `-ExecutionPolicy Bypass` が設定されています。
- **影響**: 悪意のあるスクリプトが同階層に混入された場合でも警告なしで実行されてしまうため、ゼロトラスト環境や厳格なエンタープライズ統制下では致命的な監査違反となります。
- **対策**: コードサイニング証明書を用いたPowerShellスクリプトへのデジタル署名を実施し、実行ポリシーを `RemoteSigned` もしくは `AllSigned` へ引き上げる必要があります。

### 🚨 リスク2: クラッシュ時の機密ファイル（PDF/Excel）の残留 (中〜高リスク)
**箇所**: `run_pdf2excel.ps1` 内のワークスペース管理 (`$script:runWorkspaceDir`)、`Compact-RuntimeArtifacts` 関数
**内容**:
処理の過程で `%LOCALAPPDATA%\PDF2Excel\runtime` や `output\runtime` に PDF および Excel の一時ファイルが作成されますが、処理中の強制終了や予期せぬクラッシュが発生した場合、**次回の起動処理（`Compact-RuntimeArtifacts`）が実行されるまで機密データがそのまま残留**します。
- **影響**: 共有PCなどで実行した場合、第三者が残留した機密性の高いPDF・Excelファイルにアクセスできる状態が続きます。
- **対策**: スクリプトの `finally` ブロック内で、成否にかかわらず直ちに一時ディレクトリ (`staging`, `runtime`) を強制ワイプするようライフサイクルを厳格化すべきです。

### 🚨 リスク3: `run.lock` への平文での環境・ユーザー情報の記録 (低〜中リスク)
**箇所**: `run_pdf2excel.ps1` 内の `Acquire-RunLock` 関数
**内容**:
多重起動を防止し、デバッグを容易にするため、`run.lock`（JSON形式）内に以下の情報が平文で保存されています：
- `$env:COMPUTERNAME` (マシン名)
- `$env:USERNAME` (ユーザー名)
- **影響**: `/output/runtime` などの共有される可能性のあるパスに配置された場合、システム構成情報やユーザーアカウント名が意図せず他者に露出（インフォメーション・ディスクロージャー）するリスクがあります。
- **対策**: マシン名・ユーザー名を含めるのではなく、単なる固有のインスタンスIDや、ハッシュ化した値のみを記録する仕様に変更することを推奨します。

### 🚨 リスク4: パス・インジェクションの可能性 (低リスク)
**箇所**: `Select-InputFolderDialog`, `Resolve-InputPdfFiles`, コマンドライン引数 `$InputFolder`, `$InputFiles`
**内容**:
コマンドライン引数で受け取ったパスを `Resolve-Path` で解決して使用しています。基本的には問題ありませんが、出力先やプロファイル名に細工された絶対パスや相対パス（`..\..\`など）が指定された場合、想定外のディレクトリに対するファイル作成や上書き（ディレクトリ・トラバーサル）の懸念がわずかに存在します。
- **影響**: 意図しないファイルの上書きや、保護領域への書き込み。
- **対策**: コマンドライン引数で渡されるパスに対し、`[System.IO.Path]::GetFullPath` を用いたサニタイズと、許可済みの作業ディレクトリ配下であるかどうかの境界チェックを徹底することを推奨します。

### 🚨 リスク5: M言語クエリの動的生成におけるインジェクションリスク (低リスク)
**箇所**: `Get-StagingQueryFormulaV2` 等のヒアドキュメント生成
**内容**:
PowerShell側でパラメータ（例: ファイル名、プロファイル設定値）を結合してM言語（Power Query）のスクリプトを動的に生成し、ファイル出力しています。
- **影響**: 現在は単なるテキストデータやJSON設定値のみを処理しているため悪用は困難ですが、ファイル名などに特殊な記号（`"` や `#` など）が含まれていた場合に、M言語構文やVBA側で誤動作を引き起こす可能性があります。（`Escape-MString` は実装されていますが、網羅的かの検証が必要）
- **対策**: M言語のスクリプトは静的な別ファイル（`.pq`）に切り抜き、実行時・クエリ読み込み時にPower Queryの「パラメータ」機能として安全に値を渡すアーキテクチャへの移行が推奨されます。

## 2. 評価の高いセキュアな設計ポイント
本システムでは、すでに複数の優れたセキュリティ対策およびフォールバック機構が実装されています。
* **無破壊原則（Non-Destructive）**: 元のPDFを直接操作せず、必ず `staging` にコピーを作成して処理する設計は、データの可用性と安全性を高めています。
* **認証情報の排除**: ハードコードされたパスワード、APIキー、シークレットトークンなどの機密情報はコードベース内に一切存在しません。
* **VBA無効化への耐性**: 企業のセキュリティポリシーでVBAが禁止された場合でも、PowerShellから直接xlsxとして保存するフォールバック機能が完備されています。

## 3. 総括・対応順位
PDF2Excelの現行アーキテクチャは、高いレベルでエラーハンドリングや排他制御が整理されていますが、「エンタープライズの厳格なセキュリティ要件」への対応においていくつかの負債が残っています。

**推奨される直近の対応**:
1. 異常終了時も即時クリーンアップが行われるよう、`finally` ブロックでの機密ファイル削除（サニタイズ）を徹底する（スクリプト強制終了時のOSレベルフックの導入も検討）。
2. `run.lock` に書き込まれる個人情報（ユーザー名、PC名）の秘匿化。
3. コードサイニング証明書の取得と、`ExecutionPolicy Bypass` の禁止（配布構成の変更）。
