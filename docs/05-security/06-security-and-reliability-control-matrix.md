## 1. エグゼクティブ・サマリ

現行の PDF2Excel は、単純な PDF 変換ツールというより、次の 4 つを意識して設計されています。

1. 危険な実行環境を避ける
2. 異常終了しても次回実行で回復しやすくする
3. ログやレポートで状況を追えるようにする
4. 利用者がミスしにくい導線を用意する

特に強い対策は次です。

- 共有フォルダ上での正式実行を拒否
- runtime / logs を `%LOCALAPPDATA%` へ固定
- `run.lock` と mutex による多重実行防止
- 放棄 mutex や stale `run.lock` からの回復
- ログのパスマスキング
- 環境チェックと run report による事前診断・事後把握
- レポート系と実行履歴の原子的書き込み
- 外部プロファイルの既定拒否と明示許可制

一方で、完全に無欠ではありません。残課題としては、profile schema のより厳格な検証や、保守用オプションの最小化が今後の改善候補です。

## 3. 詳細対策マトリクス

| No | リスク・障害 | 実装されている対策 | 効果 | 利用者への見え方 | 保守上の補足 |
| --- | --- | --- | --- | --- | --- |
| 1 | 共有フォルダ上で機密 PDF や一時ファイルが見えてしまう | 正式導線を `VER2 Secure` とし、共有パス実行を避ける運用に寄せている | 機密データの露出範囲を利用者端末ローカルへ限定しやすい | 正式 BAT と手順書が Secure 前提になっている | 共有保存は最終 `xlsx` のみへ寄せる運用が前提 |
| 2 | runtime や logs が共有場所に置かれて漏れる | `%LOCALAPPDATA%\\PDF2Excel\\runtime` と `%LOCALAPPDATA%\\PDF2Excel\\logs` を使用 | 一時成果物とログの置き場をローカル固定できる | 通常利用者は保存先を意識しなくてよい | `LOCALAPPDATA` が使えない端末は環境チェックで落とす |
| 3 | 危険な実行ポリシーで無署名スクリプトが動く | 正式導線の PowerShell 起動は `RemoteSigned` | `Bypass` 常用より安全 | 利用者には見えない | 保守スクリプトやテストでも `Bypass` を減らす方針 |
| 4 | 同時実行でテンプレートや出力が壊れる | OS mutex + `run.lock` の二重管理 | 多重起動を検知して安全に止められる | 「別の実行が進行中」と案内される | 排他制御の状態は環境チェックでも見える |
| 5 | 前回クラッシュ後、次回も lock に詰まる | `AbandonedMutexException` を回復扱いにする | 異常終了後でも次回実行を継続しやすい | 利用者は再実行で回復しやすい | run.lock と mutex の両方を見て状態分類している |
| 6 | `run.lock` が残って誤判定する | `実行中 / 前回異常終了の可能性 / 内容読取不可` を識別 | stale lock を単純な「失敗」と区別できる | 環境チェックで分かる | ログ確認や lock 清掃の判断材料になる |
| 7 | ログからフルパスや内部構成が漏れる | パスマスキングを既定化し、`DEBUG` 時だけ詳細表示 | 運用ログの情報露出を減らせる | 通常ログは要点だけ見える | 調査時だけ `DEBUG` で詳細を追う想定 |
| 8 | 実行結果のレポート JSON が途中で壊れる | run report を原子的に書き込み | 途中書き込みや破損を減らす | メニューが結果を安定して読める | temp file + replace 方式 |
| 9 | 環境チェックレポートが壊れる | `environment-check.md` も原子的に書き込み | 診断結果の欠損を防ぎやすい | レポート保存先を案内できる | run report と同じ堅牢化方針 |
| 10 | 実行履歴 CSV が途中破損する | `run-history.csv` を原子的に更新 | 監査証跡の完全性が上がる | 利用者は直接意識しない | CSV 追記も temp file + replace へ統一済み |
| 11 | 危険な `ProfileName` で想定外ファイルを読まれる | `ProfileName` に allowlist 制限 | パストラバーサル相当の入力を抑制 | 通常利用者は影響なし | 英数字、`_`、`-` に寄せた安全側制御 |
| 12 | 任意の外部 JSON をそのまま profile に使われる | `ProfilePath` は既定で `config/profiles` 配下のみ許可 | 信頼境界を狭められる | 通常利用者は既定 profile を使えばよい | 外部 JSON は `-AllowExternalProfilePath` 明示時のみ許可 |
| 13 | 保守者が一時 JSON を試せなくなる | `-AllowExternalProfilePath` を用意 | 安全性と保守自由度を両立 | 一般利用者には見えにくい | 保守用途だけ opt-in で使う設計 |
| 14 | テンプレート改ざんや不整合に気づけない | テンプレート整合性チェックと再生成導線 | 壊れた配布物を早めに見つけやすい | 環境チェックで検知できる | `template-integrity.json` を参照 |
| 15 | Excel COM が起動できず処理が止まる | 環境チェックで `Excel COM` 可否を事前診断 | 実行前に端末要因を切り分けできる | メニューの `[0] 環境チェック` で分かる | 初回導入時の問い合わせ削減に効く |
| 16 | 出力先やログ先に書けず失敗する | 環境チェックで output / logs 書き込みを確認 | 権限不足を先に見つけられる | 失敗前に気づける | ネットワーク制約や AV の影響確認にも使える |
| 17 | 実行結果は成功したが、利用者が出力先を見失う | 実際の出力先表示、`O/F` でファイル・フォルダを開ける | 操作ミスと確認漏れを減らせる | 完了後に迷いにくい | UI/UX 対策だが運用事故防止にも効く |
| 18 | エラー後に何を見ればよいか分からない | エラー分類ごとの次アクション案内 | 利用者の自己解決率を上げる | 画面メッセージで分かる | ログ、環境チェック、入力見直しなどへ誘導 |
| 19 | 前提条件の不足に気づかず本実行で失敗する | 環境チェックモード | 事前診断で事故を減らす | メニューから直接実行できる | 運用開始時と障害時の両方で有効 |
| 20 | 変更が回帰しても気づきにくい | unit / integration / smoke / full / legacy テスト | 主要導線と異常系の再発防止 | 利用者には見えない | 保守の品質担保基盤 |

## 4. バグ・エラー対策に絞った一覧

| 観点 | 対策 | 何を防ぐか | 現状 |
| --- | --- | --- | --- |
| 多重実行 | mutex + `run.lock` | 同時実行による出力破損 | 実装済み |
| 異常終了回復 | 放棄 mutex 回復 | 前回クラッシュ後の再実行失敗 | 実装済み |
| stale 状態判定 | lock 内容と PID 照合 | 旧 lock の誤検知 | 実装済み |
| レポート破損対策 | 原子的書き込み | 途中書き込み JSON/MD/CSV の破損 | 実装済み |
| エラー案内 | ErrorCode / ErrorCategory / guidance | 利用者の迷い | 実装済み |
| 環境差異吸収 | 環境チェック | 端末依存エラーの事前発見 | 実装済み |
| テンプレート健全性 | integrity チェック | 壊れた xlsm 配布物 | 実装済み |
| 文字コード対策 | UTF-8 BOM / ログ整形 / テスト側文字コード固定 | 文字化けやログ読解不能 | 実装済み |

## 5. 利用者向けに見ると何が安心なのか

| 利用者の不安 | 実際の対策 | 期待できること |
| --- | --- | --- |
| 「共有フォルダで勝手に見られないか」 | ローカル runtime/logs と Secure 導線 | 一時データが広く見えにくい |
| 「途中で固まったら次回も使えなくならないか」 | 放棄 mutex 回復、stale lock 判定 | 再起動後に復旧しやすい |
| 「何が原因で失敗したか分からない」 | エラー分類、環境チェック、レポート出力 | 自分で切り分けしやすい |
| 「保存先が分からない」 | 実出力先表示、開く導線 | 完了後すぐ確認できる |
| 「設定を間違えて変な JSON を読ませそう」 | 安全な profile 名制限、外部 profile の既定拒否 | 通常運用で事故りにくい |

## 6. 保守者向けの残課題

現状で特に残っている改善候補は次です。

| 優先度 | 残課題 | 理由 |
| --- | --- | --- |
| 高 | profile schema の厳格検証 | 現在は構造検査が十分に厳格とは言い切れない |
| 中 | 保守用オプションのさらに明確な分離 | 一般利用者と保守者の境界をもっと明示できる |
| 中 | セキュリティ対策の自動点検コマンド整備 | 配布前確認をさらに機械化できる |
| 低 | 対策台帳と実装参照の相互リンク強化 | 文書の追いやすさ向上 |
